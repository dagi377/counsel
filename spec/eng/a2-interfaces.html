Interfaces: API, gates, events, agent tools, module boundaries (a2-interfaces)

Scope: the contracts between Counsel's modules, its web client, firm integrations, and the Paploo agent runtime (ADR 0014, proposed). Machine-readable: a2-interfaces.openapi.yaml (OpenAPI 3.1; money endpoints in detail, the rest at path level) and a2-interfaces.json (events, tools, rules, modules, plus gate_kinds and conventions). Rules are ARC-I-###; the HTML tables below are generated from the same JSON. Most rules here are engineering contracts and cite no statute. The one tax rule (ARC-I-028) is marked (verify).

Findings that change the product spec

  • Gate ids collide across areas. G2 appears in intake, conflicts and matters. GA1/GA2 appeared in both access and trust (the trust ones are now G-TSIG/G-TREL, CF-04), G14 in conflicts and platform, and G-INT in platform and readiness. Code keys gates by a namespaced kind (trust.withdrawal); the spec id is kept only as a label (ARC-I-013). 97 kinds are mapped below. The kind prefix is the owning a4 schema (CF-05: docs, cal, conflict, matter, timekeeping, gl, core, platform, gate); a2-interfaces.json carries module_rename and renamed_gate_kinds for anyone still holding old names. Capability ids (documents.release, time.record) are permission names, not modules, and keep their spelling.
  • Counsel's gate engine is authoritative for Counsel effects (amends ADR 0014 sec. 5 for apps with their own system of record). Agent tools create gate.approval_request rows through the app API and return; the agent never opens a Paploo gate for Counsel money or trust actions. Counsel's TTL (24 to 336 h), separation of duties and sole-practitioner exception therefore govern; Paploo's 72 h default and "run owner never approves" apply only to Paploo-native gates, which never authorize a Counsel effect (ARC-I-021, -022, -045).
  • Trust withdrawals post at execution and hold funds while authorized. /execution posts the trust_transaction; bank confirmation only matches a bank line. Authorized-not-executed withdrawals reduce the available balance and reserve the bill balance, so a second withdrawal or a card payment cannot use the same money (ARC-I-025, -027).
  • Void only before delivery. After delivery the only route is a credit note (ARC-I-050).
  • ADR 0014 gates do not fit most Counsel approvals. In the ADR, the agent opens a gate and parks its step. Most Counsel gates are opened by people (a bookkeeper prepares a withdrawal), with no agent run involved. Counsel therefore needs its own gate engine for domain approvals. An agent run ends when it opens a gate, and a follow-up run starts on gate.decided (ARC-I-045). The Paploo manifest gives the agent no connector that can send anything outside the firm (ARC-I-046). As a result, the ADR's protection against a compromised app does not cover Counsel effects; Counsel's own engine provides that protection. This is open question Q1 below.
  • Paploo says irreversible always needs 2 approvers; the spec gives trust withdrawal one signatory, with a second only in dual mode. Single-signatory money kinds are classed high. Firms that turn on dual authorization get 2 approvers (dual_mode_min_approvers). The second key is that the person who executes the payment is not the person who authorized it (ARC-I-027).

2.1 Interface (shown as Go; language-neutral)

type Kind struct {
    ID              string        // "<module>.<slug>", e.g. "trust.withdrawal"
    Capability      string        // access.json capability id, e.g. "trust.authorize"
    MinApprovers    int
    DualModeMin     int           // used when firm.dual_authorization is on (trust, refund)
    Risk            Risk          // low | medium | high | irreversible
    TTL             time.Duration // default 72h
    PayloadSchema   json.RawMessage
    ExtraChecks     []Check       // e.g. IsSignatory(account, date), AuthorityLimit(amount)
    Effect          string        // registered effect handler id
}

type Engine interface {
    Open(ctx, tx, OpenInput{Kind, Subject Ref, Payload json.RawMessage,
        Preparer Principal, ExtraPreparers []UserID}) (Gate, error)          // computes payload_hash, audit, outbox gate.opened
    Revise(ctx, tx, gateID, expectedVersion int, payload, editor Principal) (Gate, error) // version+1, voids approvals, editor joins preparers
    Decide(ctx, tx, gateID, DecideInput{Decision, Version, PayloadHash, Reason,
        Decider HumanSession, SoleDeclaration string}) (Gate, error)         // SoD + capability + step-up; may insert effect_executions
    Withdraw(ctx, tx, gateID, by Principal) (Gate, error)
    ExpireDue(ctx, now time.Time) (int, error)                                // job; fail closed
    Get(ctx, gateID, viewer Principal) (Gate, error)                          // audit "viewed"
}

type EffectHandler interface {
    // key = "<gate_id>:<version>". Must be idempotent on key. Must re-check invariants. Runs in its own tx.
    Execute(ctx, tx, key string, gate Gate) (resultRef string, err error)   // err: Retryable | Permanent
}
Registry.Register(effectID string, h EffectHandler)  // at boot; unknown effect id in a Kind = boot failure

2.3 Decide checks (in order; the first failure stops)

  1. The principal is a human session (not an agent, API key or job), with MFA no older than 15 min for high/irreversible. Failure: agent_cannot_decide / step_up_required.
  2. The gate state accepts decisions and now < expires_at. Failure: gate_expired.
  3. version and payload_hash equal the current values. Failure: payload_changed.
  4. The decider is not in the preparer set (creator, editors, acting_for of agent runs, the requester of the underlying item), unless the sole-practitioner exception applies. Failure: sod_violation.
  5. The decider does not hold the admin role only. core.Can(decider, kind.Capability, subject) is true now, and the decider is not walled from the matter. Failure: missing_capability / 404.
  6. Kind extra checks pass: signatory on the date, authority limit (otherwise the decision counts as recommend), and every citation is verified.
  7. The decider has not already decided this version. Failure: already_decided.
  8. Write the gate.gate_decision row and an audit row. If approvals reach N, set the state to approved, insert gate.effect_execution(gate_id, version) (unique), and write outbox gate.decided with final=true, all in one transaction.

2.5 Exactly-once effects

  • Delivery is at least once, and the effect itself happens once. The unique key gate.effect_execution(gate_id, version) is created in the approval transaction. Every handler stores the key <gate_id>:<version> on the row it creates (a unique column), and passes the key to external providers as their idempotency key (payment refunds, e-sign, email relay).
  • Retries use backoff of 10 s, 1 m, 5 m, 30 m and 2 h. After 5 failures the state becomes effect_failed and an alert reaches the preparer and the decider. The engine never re-approves on its own.
  • Effects re-check invariants (ARC-I-024). A cooling-off gate (approved_cooling) sets effect_after, and the worker ignores the row until then.

  • The outbox row is inserted in the same transaction as the state change. A relay reads unsent rows in order (SELECT … FOR UPDATE SKIP LOCKED), hands each to in-process subscribers and to webhook delivery, and marks it sent (ARC-I-030).
  • In-process subscribers (one module reacting to another) are idempotent on event.id through the inbound_events table.
  • Payloads never carry document text, narratives, notes, email bodies or quotes (ARC-I-031). A consumer that needs content fetches it through the API, with its own authorization.
  • Changing a payload shape: adding fields keeps the same version. Removing or renaming a field means a new version, and both versions are emitted for 90 days.

3.2 Webhooks

  • Signing follows Standard Webhooks (ARC-I-033): headers webhook-id (= event id), webhook-timestamp and webhook-signature: v1,<base64 HMAC-SHA256(secret, id + "." + ts + "." + body)>. Each endpoint has its own secret, held in the vault. Rotation leaves a 24 h overlap during which both signatures are sent.
  • Delivery is at least once (ARC-I-034). Retry backoff is 5 s, 30 s, 2 m, 10 m, 30 m, 1 h, 3 h, 6 h, 12 h, 24 h; after that the event goes to dead-letter and an alert fires. Endpoints that fail for 3 days are auto-disabled.
  • Ordering is per (endpoint, subject). Only the failing subject's queue waits; other subjects keep flowing. Receivers also check subject_seq (ARC-I-032).
  • Endpoint subscriptions filter by event type. Creating an endpoint opens platform.integration_scope.
  • The Paploo direction (ADR 0014 sec. 6) uses the same signing scheme in reverse. Counsel accepts run.finished, gate.* (Paploo-side, if ever used) and artifact.published, and dedupes on webhook-id.

4. Agent tool interface

  • The tool kinds are read (no state change; free, subject to rate limits), report (plan and step bookkeeping) and write (creates a draft/proposed record and/or opens a gate). There are no tools to approve, authorize, execute, send, delete, change access or lift a wall (ARC-I-035).
  • The principal is {type: agent, run_id, acting_for}. Capabilities are the intersection of the acting user's capabilities and the agent role, and walls apply. The acting user counts as a preparer of everything the run creates, so they cannot approve it (ARC-I-016, -036).
  • Transport: tools are Counsel API endpoints exposed to the agent as an MCP server behind the Paploo MCP gateway, using the app-API org-service connection. The gateway stamps owner and run_id, and Counsel derives the principal from that stamp, never from tool arguments. Every write tool call carries Idempotency-Key = sha256(run_id + ":" + tool_call_id), so a replayed turn does not duplicate drafts.
  • Untrusted text (documents, emails, client messages) comes back in tool results as quoted data with a citation. It is never treated as instructions (ARC-I-038).

4.1 Citations

  • The brief's {doc_id, page, line, quote_hash} gains version_id, because documents are versioned and page and line numbers change between versions. It also gains line_start/line_end, because quotes span lines.
  • Page and line numbering come from read_document and /documents/{id}/versions/{v}/pages/{n}, which both use the same extracted text (document_text_pages, owned by documents). Lines are 1-based and counted after extraction, not from the visual PDF layout.
  • When a draft is created, the documents module checks each citation: it rebuilds the quote from the stored lines, hashes it and compares. A mismatch sets verified=false, and the gate refuses approval until the citation is fixed or removed (ARC-I-037).
  • Drafts reference citations with anchors in the markdown ([^c1]), mapped through the citations[] array (anchor, citation).

4.2 Plan and step reporting

  • A run must call report_plan (1–30 steps: step_id, title ≤140 chars, optional tool and depends_on) before its first write tool (ARC-I-039). Calling it again replaces the plan and keeps the history in agent_steps.
  • report_step sets a step to running|done|failed|skipped|waiting_gate, with outputs[] refs (draft ids, gate ids) and an error_code. A step in waiting_gate carries a gate_id. The run then ends, and a follow-up run starts on gate.decided (ARC-I-045).
  • The web app shows the plan and steps on the run page and in the gate card ("why am I seeing this"). Prompts, model output and conversation text are not stored, only step titles and refs.

5. Module boundaries

  • The application is a modular monolith: one deployable per cell, one Postgres database, and one schema per module (billing.bill, trust.trust_transaction; module id = a4 schema = Go package, CF-05). Each module's DB role has write grants on its own schema only, so ARC-I-040 is enforced by Postgres and not only by lint.
  • Only the owning module writes a table. Other modules call its command API in process; sharing the caller's transaction is allowed. There are two exceptions: audit.Append and platform.Publish.
  • Reads across modules go through the owner's query API, or through the api_<module> read-only views the owner publishes (ARC-I-041).
  • The money flows that cross modules:
    • A bill locks time entries through timekeeping.LockToBill.
    • A fee payment from trust goes billing → trust.RequestWithdrawal. On trust.withdrawal_executed, billing reacts and applies the amount to the bill.
    • A payment allocated to a trust ledger goes billing → trust.RecordReceipt.
    • A trust refund on a credit note goes billing → trust.RequestWithdrawal (purpose refund).
  • Effect handlers belong to the module that owns the changed state, and are registered with the gate module by id (e.g. trust.authorize_withdrawal). The gate module never writes domain tables.

This design does not mirror them, because Counsel holds the effects and a compromised Counsel defeats a mirror anyway. If the answer is yes, Paploo needs an app-opened gate (not agent-opened) in the app API, and the ADR does not have one today.
