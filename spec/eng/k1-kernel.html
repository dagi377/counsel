App kernel

Status: spec only, owner decision 2026-10-10. Nothing is built. Counsel is two layers in one repo: a reusable app kernel (kernel/), which is the generic backend for an AI-native business app, and the legal app (app/legal/) on top. This page sets the boundary, the kernel modules and their interfaces, and how the app plugs in. The build guide (o1) tags every task kernel or app, and a4-data-model.json tags every table.

Purpose

  • A second AI-native app (for example accounting or property management) should be able to reuse identity, gates, audit, events, documents, deadlines, work items, money primitives and the cell deploy without copying Counsel code.
  • Domain-free code gets stricter tests. If the gate engine has no idea what a trust withdrawal is, it cannot quietly special-case one.
  • No over-generalising. Code goes in the kernel only when it is clearly domain-free today. It stays one Go module and one repo until a second app exists (see the extraction rule below).

How the app registers

  1. app/legal/register.go exports func Register(r registry.Registry) error. It is the only symbol cmd/ calls from the app.
  2. cmd/counseld builds the kernel, calls legal.Register, then kernel.Start. Registration is boot-time only. Nothing can be registered at runtime and there is no plugin loading.
  3. Registered data (gate kinds, rule packs, document kinds, reports, portal pages, tools) must validate against spec/kernel/*.schema.json, otherwise boot fails. The app's ids use its own module prefix (billing., trust., matter.). The single exception is core.trust_signatory (CF-07), which is grandfathered under question Q-K1: rename it to trust.signatory_change with an alias?
  4. test/fixtures/helpdesk is a tiny non-legal app that registers one of each. Kernel tests run against it and never against app/legal.

Data ownership

Layer is tagged per table in a4-data-model.json (94 kernel, 103 app). Kernel schemas are core, audit, gate, platform, work and agent. App schemas are party, intake, conflict, matter, timekeeping, trust and billing. gl, docs, cal and comms are mixed: they are kernel except for the app tables listed in the DDL header. The DDL is unchanged apart from that header comment.

Known coupling: 38 kernel-table columns FK into app tables, mostly matter_id and contact_id (for example docs.document.matter_id and work.work_item.matter_id). They are listed in layers.kernel_to_app_fks and become tools/kernel_bindings.txt. Kernel Go code treats them only as an opaque Subject{Kind, ID} resolved by the app. The ratchet stops the list from growing. When a second app exists, they become (subject_kind, subject_id) through an expand-contract migration.

What stays out of the kernel, and why

  • Parties and matters. In law a "contact" means parties with adverse interest, and "matter" carries conflict and wall semantics. A generic CRM would be over-generalising.
  • Conflicts and client ID (By-Law 7.1). These are regulatory duties with legal retention.
  • Trust accounting. By-Law 9 rules (cash limit, withdrawals, three-way reconciliation) and its single-entry book of record.
  • Billing, tax and interest. Solicitors Act, ETA place of supply and the assessment rights are Ontario and Canadian law.
  • Court rule packs, legal templates and skills. These are data and content, not plumbing.
  • Time-keeping rates and rounding. They look generic, but the 8-tier rate chain and the paralegal scope are legal practice. Move them only if a second app needs exactly this.

Relation to Paploo ADR 0014 (custom apps)

Paploo runs the agent: per-user containers, connections the agent uses without holding, the tool gate, model budgets. The kernel provides the business plumbing behind the app's own API. In ADR 0014 terms, Counsel (kernel plus legal app) is the "app" with its own system of record. The kernel gate engine is authoritative for Counsel effects (ARC-I-045 amends ADR 0014 sec. 5), so a Paploo gate never stands in for a Counsel gate. kernel/agenttools is the server side of the tools that the Paploo package's skills call. The kernel holds no Paploo code, and Paploo core holds no kernel or legal terms. The kernel is not part of Paploo: a kernel app could run with no agent at all (ARC-U-028 degraded mode).

Versioning and compatibility

  • The kernel has one version, kernel.Version (semver), even while it lives in the same Go module. The Registry interface and spec/kernel/*.schema.json are CONTRACT files. Changes are additive within a major version: a new optional field or a new extension point is allowed; a removed or renamed one needs a major version and an ADR.
  • Kernel migrations follow the same expand-contract rule as the app (ARC-U-017). A kernel table never needs an app migration to apply.
  • The app declares registry.Requires(">=1.2 <2"). If it does not match, boot fails.

Extract when a second app exists

The kernel stays in this repo as kernel/ until a second real app needs it. Until then: no separate module, no plugin loading, no generic CRM, no configurable workflows-as-a-product. Extraction is a mechanical move to its own module, and it is only possible because T-001b keeps the boundary clean (no app imports, no legal terms, no new kernel-to-app FKs). At extraction time the second app's needs decide which kernel_bindings become subject references. Anything the second app does not need stays where it is.
