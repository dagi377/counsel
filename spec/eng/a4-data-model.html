A4 Canonical data model

Files: a4-data-model.sql (PostgreSQL 16 DDL, 17 schemas, 197 tables, 9 views, triggers, RLS) and a4-data-model.json (every table with columns, PK, FKs, unique/check constraints, indexes, triggers, retention, classification, plus 39 merge records). The JSON was produced by loading the SQL into a fresh cluster and reading the catalog back, so it matches the DDL.

Validation: the DDL loads cleanly with ON_ERROR_STOP=1 on a local PostgreSQL 14.18. No 16 binary was available. The DDL uses no syntax newer than 14, so it targets 16 unchanged. Smoke tests T1 to T9 (below) were run against that cluster and all behaved as expected. Docker was not used.

Key decisions

  1. No firm_id column. Each firm cell has its own database, keys and namespace, so the database itself is the tenant boundary. A firm_id on every row would protect nothing: no row from another firm can exist in the database. It would add an index column to every key and would suggest that a shared, multi-firm database is supported. Firm-level settings live in the singleton core.firm; singleton boolean UNIQUE CHECK(singleton) allows only one row. Cross-firm data (billing of the product, the fleet registry) belongs in the control-plane database, which is out of scope here. If pooling is ever needed, it is a migration that adds the column plus RLS. That is recorded as a non-goal.
  2. RLS protects access inside a firm, not between firms. Ten content tables carry policies of the form matter.can_see(matter_id). Ethical walls override everything, owners included. The system administrator never sees matter content. Access is granted by team membership, firm-open visibility or an active break-glass window. The app checks access first and RLS is the backstop. counsel_jobs bypasses RLS and is audited.
  3. One module per Postgres schema: core, party, intake, conflict, matter, docs, cal, work, timekeeping, trust, billing, gl, comms, gate, agent, audit and platform. The time area is named timekeeping because time is a SQL type keyword.
  4. Balances are derived, never stored. Trust ledger balances, bill balances, client credit and retainer funding are views over append-only rows. Overdraft protection is a deferred constraint trigger that runs at commit.
  5. One approval mechanism. Every gate (G1 to G14, GA*) is a gate.approval_request with a payload_hash, plus append-only gate.gate_decision rows. Domain tables point to the request through approval_id.
  6. One audit hash chain. Six per-area event tables are merged into audit.audit_event with a stream column. The matter timeline is the view matter.activity.
  7. Agents are not users. An agent_run has on_behalf_of, and its actions count as that human's for separation of duties.
  8. No conversation or document text in Postgres. Bodies are kept as encrypted object-store keys (*_ref). Short structured fields such as narrative, title and quote are allowed and are classed P4.
  9. Deletion policy. Financial tables are never deleted. Mutable records use archived_at. Retention destruction runs only for RC-FILE and RC-LEAD classes through matter.matter_closing.destroyed_at plus object-store purge, and is blocked by legal hold.

Review fixes (RV1, RV2, CF)

  • Ledger shape (CF-02): trust.trust_transaction is the By-Law 9 book of record. TR-1500/TR-2500 are derived from it, and gl.* is the operating book only. OP-2300 "Due to trust account" is a gl.account seed row, not DDL.
  • Gate kinds (RV2-001, CF-04): gate_code is a <module>.<slug> kind such as billing.bill_approval. The spec id (G9, G11t, G-B2, G-IMP, G-TSIG, G-TREL) goes in spec_gate. Each kind's definition is versioned in gate.gate_kind (ttl_hours, approver count, risk).
  • Withdrawal states (RV1-002): proposed, pending_authorization, authorized, executed (the trust row is posted here), applied, confirmed (bank match found). Authorized rows are holds.
  • Enums copied from b3 state machines (CF-19): bill, time entry, expense, payment and credit note statuses; time_entry.rate_source; credit_note.kind.
  • New tables (CF-03): gate.gate_kind, gate.effect_execution, trust.receipt_clearance, trust.historical_line, billing.trust_fee_transfer, billing.interest_charge, billing.write_off, billing.client_credit, billing.delivery_correction, billing.tax_period_adjustment, billing.payment_event, platform.outbox, platform.inbox, platform.idempotency_key, platform.inbound_event, platform.feature_flag, platform.source_subscription.
  • Rebilling (CF-08): a time entry or expense can sit on only one bill that is not void (partial unique index on bill_line.bill_voided). Voiding a bill releases its entries.
  • RLS (RV2-014, CF-17): RLS is enabled and forced on every table with matter_id (47 tables) except gate.approval_request and gl.journal_line. Integrity and visibility functions are owned by counsel_integrity (BYPASSRLS). counsel_jobs is created BYPASSRLS.
  • Cash limit (BIL-L-039, verify): billing.cash_received_cents(matter) adds up operating and trust cash. Callers block at 750000 cents or more, under a per-matter advisory lock.
  • Smoke: a4-data-model.smoke.sql has 68 self-checking cases, all passing on PostgreSQL 14.18. They cover each critical fix.

Notes for implementers

  • Audit writes are serialized by pg_advisory_xact_lock. Keep audit inserts at the end of transactions. This is fine at small-firm volume; if p99 lock wait goes above 50 ms, revisit with a per-stream chain.
  • FKs to gate.approval_request are plain approval_id columns. The app must check that the request is approved before it moves the domain row to an approved status. This is not a DB trigger, because the approved status differs per table.
  • The deferred FK document.current_version_id lets a document and its first version be inserted in one transaction.
  • Open questions: whether By-Law 9 retention runs from fiscal year end (trust.json). Rounding of HST per line or per bill: per bill per tax code, half-up, is assumed and must be confirmed by the billing spec owner. Whether a dual-authorization threshold is the default.
