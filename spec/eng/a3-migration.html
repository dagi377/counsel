2. Extraction plan within rate limits

  • Clio limit: 50 requests/min per token at peak (US/CA Mon-Fri 04:00-19:00 PT = 07:00-22:00 Toronto), higher off-peak, 429 with Retry-After, no custom increases (r11). Our budget: MIG-003.
  • Order: users, groups, custom field defs, contacts, matters, matter contacts, custom field values, activities (time, expense), bills, line items, allocations, credit memos, bank accounts, bank transactions, trust line items, calendar, tasks, notes, communications, folders, documents, document versions, log entries; then Reports (as of cut-over) and Document Archives per matter.
  • Each list uses fields= selection (only mapped fields + id, etag, updated_at), largest page size Clio allows (verify; 200 assumed), order=id(asc), cursor paging. Delta runs use updated_since.
  • Estimate shown before start: requests = sum(ceil(count/page)) + per-document version calls + archive polls. Example readiness mock: 18,930 docs with per-doc version calls ~= 19,000 requests -> ~6.3 h at 50/min; scheduled across nights and a weekend.
  • Checkpointing and resume: MIG-004. Raw pages staged as jsonb with sha256, retained (MIG-013, MIG-036).
  • Region: MIG-001. Firms on Clio US use a US developer app; data still lands only in the Canadian cell.

7. Trust: history, opening balances and gate G-IMP

  • Two books in two tables. Historical book = trust.historical_line: every Clio trust line, append-only, evidence and reporting only, never in a balance view. Live book = trust.trust_transaction: starts at the cut-over with exactly one kind='opening_balance' row per client ledger with a non-zero balance, approved by G-IMP. Live balance = opening + Counsel activity; history is never added on top (MIG-037, VC-TR-4).
  • Clio reconciliations are stored as trust.reconciliation rows with status='imported' and an external_signer name, so they never need a Counsel user and do not block the first Counsel sign-off (MIG-038).
  • Cut-over date = month end with a signed Clio reconciliation (MIG-031). Three-way match per account and per ledger (MIG-030, VC-TR-1..2).
  • G-IMP signatures: owner + licensee with signing authority + bookkeeper, over the exact per-ledger list and the bank statement file hash (MIG-033). Before that the trust area is locked (HTTP 423).
  • Outstanding cheques and deposits in transit at cut-over become open ReconcilingItems on Counsel's cut-over reconciliation so the first Counsel month reconciles continuously (R-17).
  • Regulatory basis: By-Law 9 s.18 (trust records: receipts journal, disbursements journal, client ledger) and the monthly comparison (s.18(8)) as cited in trust.json; retention 10 years (verify the By-Law 9 retention section on lso.ca before coding retain_until). Continuity of records across the move: readiness clio-import 'reg' (verify).

8. Alongside mode

  • Clio stays the system of record; Counsel is read-only for imported entities and trust is locked (MIG-040).
  • Webhooks for matter, activity, bill, calendar_entry, communication, contact, task, document, folder, clio_payments_payment; HMAC-SHA256 verification; payload ids only, Counsel then GETs the record (MIG-041, MIG-044).
  • Expiry max 31 days, renew at 7 days left; each subscription is a platform.source_subscription row renewed by the migration worker's hourly River job subscription.renew (MIG-042). Polling fallback and weekly delete diff (MIG-043).
  • Exit from alongside: either cut-over (runbook from R-07) or stop: delete webhooks, revoke token, keep or purge imported data on owner choice (purge keeps nothing except the audit event of the purge).

10. Audit trail preservation after migration

  • Import itself is audited: each ImportJob phase, dry-run approval, G-IMP signature and opening posting is a TrustAuditEvent / app audit event in the hash chain.
  • Clio log entries and raw staged JSON are stored as hashed archive files; their sha256 is recorded in our audit chain so later tampering is detectable. They are never converted into Counsel audit events (we do not forge authorship).
  • Historical records keep Clio author and timestamps in legacy_author/legacy_at; created_by is the import job.
  • Retention and export inclusion: MIG-036, MIG-071.

11. Our own schema and data migrations

  • Expand-contract, lock-safe DDL, batched backfills: MIG-060..062.
  • Financial history is append-only even for migrations: MIG-063. Pattern for representation changes: add column used by new rows; expose old rows through a view that derives the new shape; never backfill a financial table in place.
  • Rehearsal on anonymized per-cell snapshots inside Canada, invariant suite VC-INV-1, cell waves: MIG-064..066.
  • Migration header (required): -- budget: 120s; locks: none|brief; expand|migrate|contract; reverses: <file>|none.
